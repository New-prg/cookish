# Cookish на объектах: прототип

Ветка `refactor/object-model-prototype`. Прототип переносит Cookish на объектную модель в духе Anytype, но со специализацией под питание, спорт и покупки. Старое приложение (`mobile-shell/index.html`) не меняется. Новое живёт рядом: `mobile-shell/objects.html` и папка `mobile-shell/objects/`. У них общий origin в WebView, поэтому прототип может прочитать данные текущего приложения из `localStorage` и перенести их к себе, ничего не меняя в старых данных.

## Модель

Всё, что знает приложение, хранится как **объект** (`{ id, type, name, props, blocks?, createdAt, updatedAt, createdBy, updatedBy, archivedAt? }`).

- **Тип** задаёт название, иконку, макет и список рекомендуемых связей. Встроенные типы перечислены в `core/schema.js` (`BUILTIN_TYPES`). Человек и Ассистент могут заводить свои типы (`defineType`).
- **Связь** (relation) это глобальное свойство с форматом: `text, number, date, time, datetime, select, multiselect, checkbox, object, objects, url, formula, json`. У числа есть `min`, `max`, `unit`, `dimension`. У ссылок есть `types`. У формулы есть `formula`. Связь с `guarded: true` меняет только человек (цели КБЖУ).
- **Факт**: тип с `fact: true`. Это отметки приёмов и тренировок, расхождения, активность, покупки, записи трекеров. Факты пишет только человек или коннектор (`actor: "human" | "connector"`). Ассистент (`actor: "ai"`) не пишет факты никогда. Факты не журналируются, как сейчас История питания и Учёт.
- **Набор** (`set`) это объект с `props.query` и `props.view`. **Панель** (`dashboard`) это объект с `props.widgets`.
- **Приложение человека** (трек, экран, карточка) хранится не наборами и панелями, а своими типами. Они описаны в разделе «Набор (kit)».

## Ядро (готово)

- `core/schema.js`: встроенные связи и типы, таблица MET.
- `core/formula.js`: разбор и вычисление формул без eval, лимиты (`LIMITS`), таблица функций (`registerFunctions`). `Ref` оборачивает ссылку на объект внутри формулы.
- `core/values.js`: `valueOf(state, objOrId, rel, ctx)` возвращает значение связи, формулы считаются по требованию и кэшируются на снимок. `displayValue` даёт строку для показа. `backlinks`, `objectsOfType`, `profileOf`, `formulaError`.
- `core/functions.js`: формульные функции домена `kcalOf`, `nutrientOf`, `burnedOf`, `met`.
- `core/query.js`: `runQuery(state, { source, filters, sorts, group, aggregates, limit }, ctx)` и `runSeries(...)` для графиков. Источник это `{ type }`, `{ ids }` или `{ builtin, args }` из `registerSource`. Токены дат: `@today`, `@yesterday`, `@tomorrow`, `@+Nd`, `@-Nd`, `@lastNd`, `@nextNd`, `@thisWeek`, `@thisMonth`.
- `core/store.js`: `openObjectStore({ storage, key, clock, today, idFactory })`. Запись только через `apply(ops, { actor, summary })`, операции `create, update, archive, restore, defineType, defineRelation, revert`. Пачка атомарна. Проверки: связи и форматы, ссылки на существующие объекты нужных типов, факты, охраняемые связи, одиночки (`singleton`), правила домена (`registerRule`). Журнал (`state.journal`, до 200 наборов) и откат `revert(changeSetId)`. `replaceAll(state)` для разового импорта. `subscribe(fn)`.
- Тесты: `tests/objects-core.test.mjs`.

`ctx` для чтения всегда `{ today: "ГГГГ-ММ-ДД" }`, его даёт `store.today()`.

## Как моделируется Рацион и Спорт

- **Неделя плана** (`week_plan`): `area` (`ration` или `sport`), `effectiveFrom`, `anchor`, `weekdayBinding`, `days` (упорядоченные `day_plan`). Это бывшая Версия с её Циклом. В интерфейсе слово «Цикл» не показываем.
- **День плана** (`day_plan`): `area`, `meals` или `sessions`. У дня цикла есть `cycleIndex`, у Особого дня есть `date`.
- **Приём пищи** (`meal`): `time`, `items` (порции), `slot`. **Порция** (`portion`): `product`, `amount`, `unit`, `packSize`. КБЖУ считается формулами.
- **Тренировка** (`session`): `kind`, `time`, `duration`, `intensity`, `note`, `slot`.
- **Слот** (`slot`) это устойчивый ключ приёма или тренировки. Копия дня цикла в Особый день получает новые id объектов, но тот же `slot`. Отметки ссылаются на дату и слот, поэтому переживают копирование, как сейчас `history.meals[mealId]`.
- **Отметка приёма** (`meal_mark`, факт): `date`, `slot`, `meal`, `mealState`, `transferredMinutes`. **Расхождение** (`discrepancy`, факт): `date`, `slot`, `discrepancyKind`, `product`, `replacedBy`, `amount`, `unit`. **Отметка тренировки** (`session_mark`), **Активность** (`activity`).
- Покупки: **Запрос** (`request`) со `status` и `items`, **Позиция запроса** (`request_item`), **Покупка** (`purchase`, факт) ссылается на позицию и запрос. Куплено и потрачено считают формулы по обратным ссылкам.

## Домен (`core/domain.js`, делает агент домена)

Экспортирует ровно это, интерфейс опирается на эти имена.

```js
planDay(state, area, date) // → { dayId, source: "special"|"cycle"|"empty", weekId, items: [id] } items по времени
markFor(state, area, date, slot) // → объект meal_mark или session_mark или null
dayActual(state, date, ctx) // → { planned: {kcal, protein, fat, carbs}, eaten: {...}, meals: [{ mealId, slot, state, planned, actual, discrepancies: [id] }] }
sportDay(state, date, ctx) // → { planned, actual, sessions: [{ sessionId, slot, state, planned, actual }], activities: [id] }
markMealOps(state, date, mealId, mealState) // → ops
discrepancyOps(state, date, mealId, { kind, product, replacedBy, amount, unit }) // → ops
markSessionOps(state, date, sessionId, sessionState, { actualDuration, actualIntensity } = {}) // → ops
editableDayOps(state, area, date) // → { ops, dayId, idMap } Особый день из дня цикла, idMap: старый id → новый
newWeekOps(state, area, { fromDate, days }) // → ops новая неделя плана с даты, только будущее
requestFromPlanOps(state, { dates, name }) // → ops Запрос с округлением до упаковок
markBoughtOps(state, itemId, { quantity, price, date }) // → ops
```

Источник для наборов: `registerSource("plan", (state, { area, date }, ctx) => ids)`, где `date` может быть токеном `@today`.

Правила (`registerRule`): прошлое плана неизменно, дневная проверка КБЖУ для `actor: "ai"` с порогами из `mobile-shell/core/proposals.js` и `core/safety.js`.

## Наборы и виджеты: точная форма

```js
// Набор: объект типа set
props.query = { source: { type } | { ids } | { builtin, args }, filters, sorts, group, aggregates, limit } // как в runQuery
props.view = { layout: "list" | "table" | "kanban" | "calendar" | "gallery" | "checklist", relations: [relKey], groupRel?, dateRel? }

// Виджет: элемент массива props.widgets у объекта типа dashboard
{ id, kind: "ration-today" | "sport-today" | "requests" | "set", title,
  setId, display: "list" | "number" | "bars",           // только для kind "set"
  aggregate: { rel, fn },                              // для "number", по умолчанию { fn: "count" }
  series: { dateRel, valueRel, fn, range: "@last7d" }, // для "bars"
  goal }                                               // необязательно: «X из goal»
```

## Набор (kit)

Папка `mobile-shell/objects/kit/`. Слово «набор» в этом документе значит две разные вещи. Набор (`set`) это сохранённый запрос из раздела выше. Набор (kit) это конструктор приложений человека. Из его деталей человек или ИИ собирает учёт воды, привычку, список сборов или справочник, не трогая код. Приложение человека не использует `set` и `dashboard`.

Хранилище остаётся единственным источником правды. Из него по требованию читается **Спецификация** (`kit/spec.js`, `readSpec`). Это треки с полями и пунктами, экраны и карточки. Её не сохраняют, у хранилища нет второй копии. `printSpec` печатает Спецификацию обратно в виде пакета, для модели и для экспорта. Любое изменение приходит как пакет, а `kit/pipeline.js` превращает его в операции хранилища и применяет одним набором изменений.

Полный словарь лежит в `kit/catalogue.js`. Виды, типы полей, единицы, расписания, периоды, функции, виртуальные величины, элементы со всеми атрибутами и лимиты (`LIMITS`) записаны там один раз. Валидатор, нормализатор, значения по умолчанию, проверка разметки и руководство для модели читают этот файл. В документе словарь не повторяется, чтобы он не разошёлся с кодом.

### Что есть что и где лежит

| Понятие | Что это | Как хранится |
|---|---|---|
| Трек | Всё, что человек ведёт. Вода, привычка, список, справочник. | Свой тип `tr_<трек>`. `fact: true` у видов log, habit, list и follow, `fact: false` у catalog. Настройки лежат в `type.kit` (`track, kind, states, labels, unmarked, grace, times, per, follows, avoid, app, since`). Убранный трек получает `hidden` и `kit.archived`. |
| Поле | Один вопрос трека. Сколько, оценка, вариант, ссылка. | Связь `tr_<трек>__<поле>`, описание в `kit` (`track, field, type, goal, goalType, goalPer, planned, on, required, hint, labels, to, calc`). Тип `choice` хранится как `select` с id `o1, o2…`. Тип `calc` хранится как `formula`, локальные ключи в ней заменены на ключи связей (`rewriteCalc`). Тип `link` хранится как `object` с типом `track_item` или `product`. |
| Пункт | Строка расписания (habit, list) или справочника (catalog). | Объект типа `track_item`, id `ti_<трек>_<пункт>`. Свойства `kit_track, kit_key, kit_every, kit_at, kit_from, kit_until, kit_plan`. |
| Запись | Одно измерение, которое внёс человек. Запись также бывает у привычки или списка, если она не из расписания. | Объект типа `tr_<трек>` со свойствами `date` и значениями полей. |
| Отметка | Ответ «сделал», «изменил» или «пропустил» на пункт за день. У вида follow это ответ на приём пищи или тренировку. Отметка это факт. | Тоже объект типа `tr_<трек>`, но со ссылкой `kit_item` на пункт или с `kit_slot` (слот приёма) и со статусом `kit_state` (`done`, `changed`, `skipped`). |
| Экран | Страница приложения. Экран `home` есть всегда. | Объект `kit_screen`, id `sc_<ключ>`. Свойства `kit_key, kit_order, kit_icon, kit_app`. Экран `home` хранится, только когда на нём есть карточка. |
| Карточка | Блок экрана с заголовком и элементами, от одного до четырёх. | Объект `kit_card`, id `cd_<ключ>`. Свойства `kit_key, kit_screen, kit_size, kit_order, kit_app, kit_body`. В `kit_body` лежит дерево элементов (JSON), подпись лежит в `description`. |

Остальное, что нужно знать о хранении.

- Все `id` выводятся из ключей. Один и тот же пакет, применённый дважды, во второй раз не даёт ни одной операции (`noop`).
- `kit_app` это слаг названия пакета, который создал объект. По нему точно находится «всё приложение целиком» для экспорта (`kit/share.js`).
- Связи `kit_*` и типы `track_item`, `kit_screen`, `kit_card` системные и скрыты в библиотеке. Они описаны в `core/schema.js`.
- Классические разделы `ration`, `sport` и `shopping` видны Спецификации как треки только для чтения. Их числа читаются через `domain.js`. Набор в них ничего не пишет, а их ключи и ключ `home` нельзя занять под свой трек.
- Что отметка значит, решается при чтении, в `kit/ledger.js`. `resolveOccurrence` сводит срок пункта и отметки в состояние `done`, `changed`, `skipped`, `pending` (сегодня ещё можно отметить) или `none`. Для прошлого дня без отметки состояние задаёт правило `unmarked`. Отметка «изменил» заменяет плановые значения пункта, а у пропущенного числа равны нулю. `dayStatus` даёт день `ok`, `missed`, `open` или `none`. `streakOf` считает серию с запасом `grace` пропущенных дней. Все графики трека с пунктами читают `points`, а не сырые записи. Величины `done, skipped, due, rate, open, count` считает код, они не хранятся и зарезервированы, поэтому поле с таким ключом нельзя завести.

### Пять видов

Вид (`kind`) это набор значений по умолчанию, а не отдельный тип в хранилище. Одна функция `expandDefaults` (`kit/defaults.js`) превращает короткое объявление в полное. Руководство для модели печатает свою таблицу, вызывая ту же функцию. Значения по умолчанию получает только новый трек. Карточки по умолчанию добавляются, только если ни один элемент пакета не упоминает этот трек.

| Вид | Что хранит | Кнопки отметки | `unmarked`, `grace` | Карточки по умолчанию |
|---|---|---|---|---|
| `log` Журнал | Свободные записи, сколько угодно в день. Без пунктов. | Нет | Нет | На главную форма записи, а перед ней шкала цели, если у поля есть цель. На экран трека столбцы по дням (или линия, если величина не складывается) и список последних записей. |
| `habit` Привычка | Пункты по расписанию и одна отметка на пункт и день. Незапланированные записи тоже можно вносить. | `done`, `skipped` | `ignore`, `0` | На главную отметки. На экран трека серия и календарь доли выполненного за 12 недель. |
| `list` Список | Пункты без расписания (`every: "open"`), каждый отмечается один раз. | `done` | `ignore`, нет | На главную число оставшихся. На экран трека отметки с добавлением пунктов, а при поле в рублях ещё сумма за месяц. |
| `catalog` Справочник | Только строки, то есть пункты. Не факт. На строки ссылаются поля других треков. | Нет | Нет | Только на экран трека, список строк. |
| `follow` Дополнение к приёмам | Одна отметка на приём или тренировку из Рациона или Спорта (`follows`). | `done` | `ignore`, нет | На главную отметки. На экран трека линия по первому числовому полю и таблица последних отметок. |

Привычка с `avoid: true` («не делать») переворачивает значения. Пропуск считается удавшимся днём (`unmarked: "assumed"`), кнопки называются «держусь» и «сорвался», серия считает дни без срывов. Новый пункт привычки получает `every: "day"`, пункт списка получает `every: "open"`, оба получают `from` равным дню создания. Новая цель получает `goalType: "min"` и `goalPer: "day"`.

### Пакет и правка

Пакет это JSON-объект `{ v: 2, name, reply?, tracks?, screens?, remove? }`. Форма каждой части описана в `kit/catalogue.js` (`BUNDLE_ATTRS`, `TRACK_ATTRS`, `FIELD_ATTRS`, `ITEM_ATTRS`, `SCREEN_ATTRS`, `CARD_ATTRS`, `ELEMENTS`). Глубина фиксирована. Пакет содержит треки и экраны, экран содержит карточки, карточка содержит элементы без вложенности. Модель не пишет `id`, версии и операции хранилища.

```json
{ "v": 2, "name": "Чтение",
  "tracks": [{ "key": "pages", "name": "Страницы", "kind": "log",
    "fields": [{ "key": "n", "name": "Прочитано", "type": "number", "unit": "стр.", "goal": 30 }] }] }
```

Этот пакет создаёт трек, а карточки на главную и на экран «Страницы» добавляет `expandDefaults`. Создание и правка выглядят одинаково, и это главное решение набора. Правка идёт наложением по ключу (`kit/merge.js`, `mergeBundle`).

- Ключ, которого нет в пространстве, создаёт новое. При создании обязательны `name` и `kind` у трека, `name` и `type` у поля, `name` у экрана, `title` и `body` у карточки.
- Ключ, который уже есть, меняет только написанные атрибуты. Цель в 40 стр. задаёт пакет `{ "key": "pages", "fields": [{ "key": "n", "goal": 40 }] }`. Цель снимает `goal: 0`.
- Карточка с `body` заменяет тело целиком. Плановые значения пункта (`plan`) и подписи кнопок (`labels`) сливаются по ключам.
- Поле `order` у экрана перечисляет ключи карточек. Перечисленные встают первыми в этом порядке, остальные идут следом.
- `remove` убирает по одному ключу в записи. Допустимы `{ card }`, `{ track }`, `{ screen }`, `{ item: "трек.пункт" }` и `{ field: "трек.поле" }`.
- Убранное архивируется, а не удаляется. Записи убранного трека остаются, и объявление трека с тем же ключом возвращает его. Элементы, которые читают убранный трек, уходят из карточек. Убранное поле убирает элемент, если читает его в `value`, `category`, `sort`, `values` или `where`, а из списков `columns` и `fields` только вычёркивает ключ. Карточка, у которой не осталось элементов, убирается. Каждое такое следствие (`cascades`) попадает в строки предложения, и человек его видит.
- Порядок удаления в пакете фиксирован. Сначала карточки, поля и пункты, затем экраны, затем треки.

Результат `checkBundle` кроме операций содержит `rows`. Это строки изменений на языке человека («Новое поле», «Изменится карточка», «Уберётся трек»), по ним строится карточка Предложения.

### Слои проверки

Пакет проходит слои по порядку. Модель видит только проблемы первого слоя, где они нашлись, и не больше шести (`MAX_PROBLEMS`). Проблема это `{ path, rule, message, allowed? }`. Путь называет ключи, а не номера (`tracks.water.fields.ml.goal`).

| Слой | Где живёт | Что проверяет |
|---|---|---|
| L0 | `kit/normalize.js` (`normalizeBundle`). В поверхности HTML до него `kit/markup.js` (`bundleFromMarkup`) проверяет грамматику тегов. | Разбирает ответ в объект. Чинит только промахи с одним прочтением (регистр, `-` в ключах, `yes` и «да», форматы чисел, списки через запятую, словесные формы периодов и расписаний, псевдонимы единиц) и сообщает о каждой правке. Всё, что читается двояко, оставляет слою L1. |
| L1 | `kit/validate.js` (`validateBundle`) | Три прохода. Форма и словарь по каталогу. Ссылки `of`, `value`, `where`, `to` против пространства и пакета, правила видов, разбор формул, лимиты. Нижние пределы безопасности. Вызывается дважды, второй раз после `expandDefaults`. |
| L2 | `kit/pipeline.js` (`checkBundle`) | Пакет сливается с Спецификацией (`merge.js`), переводится в операции (`lower.js`) и выполняется как `actor: "ai"` на копии пространства. Хранилище отказывает фактам, охраняемым связям, правилам домена и правилам набора (`rules.js`). |
| L3 | `kit/markup.js` (`checkCardMarkup`) поверх `viz/validate.js` (`validateMarkup`, режим `kit`) | Разметка каждой созданной или изменённой карточки. Только известные теги и атрибуты. `screen.js` проверяет карточку ещё раз перед отрисовкой. Не прошедшую он заменяет заметкой «Карточка не показана». |
| L4 | `viz/audit.js` (`auditRendered`) | Отрисованный экран в браузере. Выход за край, цели нажатия меньше 44x44, пустое состояние, наложенные подписи, текст в цвете ряда, статус одним цветом, элемент ввода без подписи. Слою нужен браузер, поэтому `checkBundle` его не запускает. Его запускают стенд (`check.mjs`) и тесты. |

L0, L1 и L3 чистые функции. L2 выполняет операции на копии пространства. Ни один слой не пишет в настоящее пространство. Ответ только со словами в `reply`, без треков и экранов, это отказ или вопрос. Он проходит L0 и L1 (в том числе правило чисел), и `checkBundle` возвращает `noop`.

`kit/author.js` (`authorBundle`) держит цикл. Модель получает руководство и просьбу, ответ проходит слои, а проблема первого сломавшегося слоя возвращается одним сообщением. Исправлений не больше двух (`maxRepairs`). После последнего человек получает честный отказ с проблемами и ничего не применяется наполовину.

### Элементы ввода

Элементы живут в `kit/inputs.js`: `c-quick` (кнопка с готовым значением), `c-form` (форма записи), `c-marks` (отметки на сегодня), `c-add` (добавление строки под списком с `add`), `c-streak` (серия) и `c-embed` (готовый блок Рациона, Спорта или Покупок). Они подчиняются одному правилу. Запись делает только человек.

1. Элемент данные не ищет. Ему отдаёт готовую форму `resolveBinding` из `kit/bind.js`.
2. Элемент хранилища не касается. Нажатие он превращает в событие `kit-action` с закрытой записью (`do: quick | form | mark | unmark | addItem`).
3. `kit/screen.js` (`wireActions`) переводит запись в операции через `kit/actions.js` (`quickOps`, `formOps`, `markOps`, `unmarkOps`, `addItemOps`, `entryOps`). Эти функции ничего не пишут, только возвращают операции.
4. Операции применяются через `applyUndoable` с `actor: "human"` и с кнопкой «Отменить» в уведомлении.

`actions.js` проверяет значение до записи. Число лежит в границах поля, обязательное поле заполнено, `calc` записать нельзя, ссылка указывает на живую строку справочника, будущий день нельзя. Отказ приходит как русское сообщение и показывается уведомлением. Хранилище в любом случае отказывает фактам от `ai`. Под приёмом пищи в дне Рациона и под тренировкой в дне Спорта `followControls` показывает отметки треков вида `follow`.

### Правила безопасности, которые остаются в коде

Правила не зависят от того, что написала модель, и не лежат в тексте руководства.

- **Нижний предел энергии.** Цель в `ккал` ниже 1200 в день отказывается. Поля, названные расходом или тренировкой, исключены.
- **Дозы не считаются.** Поле `calc`, которое читает единицы доз (`мг`, `мкг`, `МЕ`, `таб.`), отказывается. Дозу приложение только записывает и показывает трендом.
- **Числа о человеке.** В заголовке, подписи, подсказке, тексте и `reply` число должно быть из привязки элемента, из атрибутов пакета или из просьбы человека. Иначе текст отказывается. Число считает элемент, а не модель.
- **Один код на две двери.** Первые два правила описаны в `kit/rules.js` (`safetyFloors`). Валидатор вызывает их для фактов пакета, а правило хранилища (`registerKitRules`) для каждой пачки от любого актора. Правило чисел работает только в валидаторе, потому что хранилище не знает просьбы.
- **Записи.** Нельзя внести или отметить будущий день, на пункт и день не бывает второй отметки. Факты пишет только человек, ни пакет, ни `propose_objects` их не создают. Операции пакета содержат только структуру.
- **Закрытый словарь.** Скриптов, ссылок, картинок и обработчиков нет. Разметка карточки состоит из слов каталога, а то, чего приложение не умеет рисовать, не показывается.
- **Классические разделы** читаются и не пишутся. Убранное архивируется, данные остаются.

### Руководство для модели

`kit/manual.js` (`renderManual(state, { surface, request, today })`) собирает системное сообщение модели, которая строит приложение. Части идут по порядку (`manualParts`). Договор об ответе, устройство приложения, словари, объявления, элементы, таблица «что приложение добавляет само», правила, примеры, сводка пространства человека и сама просьба.

- Списки, атрибуты и пояснения печатаются из каталога. Таблица умолчаний печатается вызовом `expandDefaults`. Сводка пространства печатается из `printSpec`. После 4800 знаков сводка теряет подробности шаг за шагом и оставляет ключи.
- Примеры лежат в `kit/examples/*.json` как пакеты. К просьбе подбираются три по тегам (`pickExamples`). Если в пространстве уже есть треки, среди трёх бывает пример правки. В поверхности `html` пример печатает `bundleToMarkup`.
- Типичные промахи слабой модели записаны в `MISTAKES`. Тест проверяет, что валидатор действительно называет каждый из них.
- Бюджет задан в `MANUAL_BUDGET` (цель 7000 токенов, предел 9000). Тест проверяет его для пустого, демо и разросшегося пространства.
- Поверхностей две. `json` по умолчанию и `html`, где пакет записан тегами `<c-bundle>`. Это два написания одного пакета.
- Часть руководства, которая не зависит от человека, возвращает `renderReference(surface)`. Ассистент получает её в описании инструмента `propose_space`.

**Почему руководство не называет темы корпуса.** Руководство читает слабая модель (Claude Haiku 5.5), а стенд ставит оценку по запросам из `scripts/primitives-lab/corpus.json` и `holdout.json`. Если пример в руководстве называет воду, вес или жим, ответ на запрос корпуса уже написан, и оценка измеряет списывание. Поэтому `kit/examples/` и образцы `FIELD_SAMPLES`, `ELEMENT_SAMPLES` и `PAIR_SAMPLES` в `manual.js` берут свои темы (заплыв, коктейли, сумка в зал). Поля `example` в каталоге называют темы корпуса (`water`, `ml`, `bench`), поэтому руководство их не печатает и подставляет свои образцы. Два теста в `tests/kit-manual.test.mjs` держат это правило. Один ищет основы запрещённых слов в примерах, другой в тексте `renderReference` и в образцах.

### Стенд (`scripts/primitives-lab/`)

Стенд проверяет, что слабая модель строит из руководства нужные приложения. Корпус это `corpus.json` и `holdout.json`, у каждой просьбы есть `category`, стартовое пространство (`empty`, `demo` или `after:<id>` для продолжения) и проверки возможностей. Запросы с `refuse` ждут отказа. Все команды запускаются из корня репозитория.

```
node scripts/primitives-lab/spaces.mjs
node scripts/primitives-lab/prepare.mjs <json|html> <runDir> [id | cat:<категория>] [--set corpus|holdout]
node scripts/primitives-lab/waves.mjs <corpus|holdout> [id | cat:<категория>]
node scripts/primitives-lab/check.mjs <json|html> <runDir>/<поверхность>/<id>
node scripts/primitives-lab/judge-packet.mjs <runDir>/<поверхность>/<id>
node scripts/primitives-lab/report.mjs <runDir>
```

1. `spaces.mjs` собирает два стартовых пространства (`empty`, `demo`) в `output/primitives/spaces/`. Запустите его до первого `prepare.mjs`.
2. `prepare.mjs` делает папку на каждую просьбу. В ней `item.json`, `state-before.json`, `prompt.md` (руководство и просьба) и `task.md`. Продолжение (`after:`) ждёт, пока у родителя появится `state-after.json`. Повторный запуск не трогает просьбу, у которой уже есть попытки.
3. `waves.mjs` печатает цепочки (`{"chains": [[корень, продолжение, …]]}`). Цепочки независимы и идут параллельно, внутри цепочки по порядку.
4. Модель-строитель (текст задания в `haiku-prompt.md`) читает только `prompt.md`, пишет `answer.json` или `answer.html` и запускает `check.mjs`. Проверка гоняет слои L0 до L3 (`checkBundle`), применяет пакет, отрисовывает изменённые экраны в браузере, запускает L4, делает скриншоты `screen-*.png` и пробные нажатия. При проблеме печатает не больше шести строк «путь: сообщение» первого сломавшегося слоя и завершается с кодом 1. Если всё прошло, печатает «Готово» и завершается с кодом 0. Код 2 означает сбой стенда, это не попытка. Исправлять разрешено дважды, то есть проверка идёт не больше трёх раз. Каждый запуск дописывает строку в `attempts.jsonl` и переписывает `verdict.json`.
5. `judge-packet.mjs` пишет `judge.md` (просьба, проверки, ответ строителя человеку, описание построенного, пробные нажатия, итог L4, пути скриншотов) без текста ответа и без числа попыток. Модель-судья читает его по `rubric.md` и `judge-prompt.md` и пишет `judge.json`. Вердикты `fit`, `partial`, `miss`, `wrong-refusal`, `correct-refusal`.
6. `report.mjs` собирает `report.json` и `report.md` по файлам прогона.

Остальное. `example-answer.mjs <поверхность> <папка> <id примера | bundle.json>` кладёт заведомо верный ответ в папку просьбы, так проверяют сам стенд. `load-test.mjs <runDir>` запускает `check.mjs` на всех папках сразу. `selftest.mjs` доказывает, что работает сам стенд (нужен браузер).

Тесты набора. Они не входят в `npm test`.

```
node --test tests/kit-bundle.test.mjs tests/kit-logic.test.mjs tests/kit-manual.test.mjs
node --test tests/kit-element.test.mjs tests/objects-ui-kit.test.mjs
```

Первая команда работает без браузера и проверяет пакет, слои, движок отметок и руководство. Вторая открывает приложение в браузере и проверяет элементы и экраны.

## Сборщик (`core/builder.js`, `ui/builder.js`, `kit/author.js`)

ИИ собирает приложение человека из деталей набора (kit). Экран «Собрать с ИИ» передаёт слова человека в `buildProposal`, тот вызывает `authorBundle`. Модель получает руководство (`renderManual`) и сводку пространства. В сводке есть ключи, названия, виды, поля с единицами и целями, ключи пунктов и то, что показывает каждая карточка. Текста объектов и записей в ней нет. Модель отвечает пакетом и коротким `reply`. Пакет проходит слои L0 до L3, как описано выше. Предложение состоит из `reply`, названия изменения и строк изменений (`rows`). Применяет его человек кнопкой, `applyBundle` пишет всё одним набором изменений, и откат `revert` отменяет весь пакет целиком. Пока окно открыто, разговор сохраняется, и вторая просьба строится на первой.

Старый язык операций (`defineRelation`, `defineType`, `createSet`, `addWidget`) удалён. Сборщик и `propose_space` принимают только пакет.

## Ассистент (`core/assistant.js`, `assistant-plan.js`, `assistant-safety.js`, `ui/assistant.js`)

Старый ассистент на объектах. Цикл с инструментами как раньше, но читает объекты и отвечает Предложениями. Каждый прогон открывает черновую копию пространства (`openObjectStore({ storage: null })`), повторяет на ней ожидающие Предложения разговора и выполняет каждое новое как `actor: "ai"`: правила хранилища (нет фактов, охраняемые связи, прошлое плана, дневная проверка КБЖУ) отказывают сами, отказ возвращается модели как `problems`. Реальное пространство меняет только человек кнопкой «Применить», это один шаг журнала, отмена через `revert`.

- Чтение: `get_space` (в поле `kit` лежит сводка приложения человека), `find_objects`, `get_object`, `get_plan`, `get_history`, `get_profile`, `get_change_sets`, `find_reference`, `search_food`.
- Запись (только Предложения): `propose_day` (Особый день целиком), `propose_week` (новая неделя с завтрашнего дня), `propose_objects`, `propose_space` (пакет набора, треки, экраны и карточки), `propose_revert`. Новый продукт идёт в `new_products` того же Предложения, цифры карточки берёт код.
- `propose_space` принимает `{ summary, bundle }` и прогоняет пакет через `checkBundle` на черновой копии. Числа, которые назвал человек в разговоре, считаются источником для правила чисел. Первый сломавшийся слой возвращается модели как `problems`. Строки предпросмотра берутся из `rows`. Описание инструмента несёт `renderReference("json")`.
- `propose_objects` не меняет `track_item`, `kit_screen` и `kit_card`. Записи в треки ассистент не вносит, это факты.
- Защитный режим (`assistant-safety.js`): несовершеннолетний в профиле или признаки РПП (слова человека, частые «не съедено» за 14 дней) запрещают Предложения, которые снижают еду или добавляют нагрузку. Правила и пороги те же, что в `core/safety.js`, тест сверяет оба на одних данных.
- Разговор хранится в `localStorage` `cookish.objects.assistant.v1`; при открытии экрана ожидающие Предложения проверяются заново (статус `conflict`).

## Интерфейс (`objects.html`, `objects/ui/`, делает агент интерфейса)

Anytype для питания, спорта и покупок: главная панель с виджетами, библиотека типов и наборов, вид набора (список, таблица, канбан, календарь, галерея, чек-лист), страница объекта со связями, создание своих типов и связей, день Рациона и день Спорта, Запрос с отметкой покупки, отмена через журнал.

Приложение человека из набора (kit) показывает `kit/screen.js` (`mountScreen`). Карточки экрана `home` стоят на главной вместе с панелью, список «Мои разделы» ведёт на остальные экраны. Отметки треков вида `follow` стоят под приёмом пищи и под тренировкой в днях Рациона и Спорта. Кнопка «Собрать с ИИ» открывает Сборщика.
