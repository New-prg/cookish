Цель плана

Перевести Cookish с синхронизации через Google Sheets на backend source of truth, сначала получить полностью повторяемый запуск и тестирование backend в локальном Docker Compose, затем перенести те же immutable images и конфигурацию на любой Linux VPS по SSH. Сохранить offline-first UX, завершить контур «план → покупка → факт» и опционально подключить Health Connect. AI и Huawei Health не реализуются в рамках этого плана. Архитектура сохраняет для них стабильные extension points, но release Architecture v4 не зависит от моделей, AI-провайдеров, HMS SDK или Huawei approval.

00b · Non-negotiables across all blocks
Always
  • Offline core flows (list, check buy, meal log) work without network
  • Idempotent ops via clientOpId
  • One local repository and one server conflict path; no dual JS+Java domain writers
  • Server assigns canonical revisions; device clocks are metadata, not conflict authority
  • Security, deletion, retention and observability ship with each data class
  • Future integrations use versioned commands/read models; core never depends on AI or a health vendor
Never in early blocks
  • Diet-coach gamification / medical claims
  • Retailer scraping
  • AI runtime, model keys, prompts, agent UI or autonomous writes
  • Huawei HMS SDK, Health Kit scopes, provider picker or Huawei QA
  • Blocking main app on Health Connect availability
  • Big-bang rewrite of UI before sync works
00c · Local-first runtime · provider-neutral SSH target
Prove locally, ship the same images remotely DECIDED BASELINE
flowchart LR D[Developer or CI] -->|docker compose up| L[Local Docker network] L --> A[Cookish API] L --> P[(PostgreSQL)] L --> M[Migration one-shot] T[Contract + integration tests] --> A CI[CI builds image by Git SHA] --> R[OCI registry] R -->|SSH deploy after local gate| V[Generic Linux VPS] V --> C[Caddy: TLS + reverse proxy] C --> A2[Same API image] A2 --> P2[(Private PostgreSQL)] P2 --> O[Encrypted off-site backup]

Сначала весь backend-контур доказывается локально без аренды сервера: schema migrations, auth stubs, API, Postgres, jobs, contract/integration tests, seed/reset и backup/restore. VPS появляется только после зелёного local/CI gate и получает те же образы и Compose-модель через SSH.

Local Docker first
  • One command starts API, PostgreSQL and migrations from a fresh clone
  • Separate dev and test databases; deterministic fixtures and reset command
  • No production credentials, domains, TLS or rented infrastructure needed
  • Contract, migration, restart and restore tests run locally and in CI
Remote only after the gate
  • Generic Ubuntu LTS host reached through standard SSH; no provider API dependency
  • Production override adds Caddy, persistent volumes, restart policy and real secrets
  • PostgreSQL remains private; deploy and rollback use immutable Git-SHA images
  • Off-site backups, external monitoring and replacement-host restore remain our responsibility
Portability rule

Core deployment must require only Docker Engine, Compose and POSIX SSH. Provider panels, snapshots, rescue consoles and APIs may be documented later as optional operational accelerators, but they never enter the application, migration or rollback contract.

B1 — Deployable and recoverable platform INFRA
# Work item Notes

1.2 Deterministic local test profile Isolated test DB, fixtures, seed/reset commands, migration up/down compatibility checks and no dependency on developer-machine state
1.3 Provider-neutral production overlay compose.prod.yaml adds Caddy, persistent volumes, restart policy and production healthchecks; Postgres port is never public

1.6 Household create / join / leave; expiring invite code; membership roles Replaces spreadsheet link mental model; authorization is household-scoped
1.7 Device registration + sync cursor table deviceId, lastAckRev, lastSeenAt, retiredAt

1.11 Refresh-token rotation, revoke/logout, account deletion/export Encrypted-at-rest token storage; replay detection; audit trail
1.12 Two-layer backup and recovery Encrypted PostgreSQL base/WAL or logical backup to independent off-site storage; optional host snapshot is convenience only; scheduled retention, integrity check and clean restore
1.13 Provider-neutral VPS incident runbooks Reboot, disk-full, lost SSH, OS reinstall, restore to replacement VPS and DNS switch; provider-specific recovery notes may be appended later
In scope

Identity + household + empty sync endpoints, plus repository-owned infra/runtime Compose, test, bootstrap, deploy, backup and restore artifacts.

Out of scope

AI, Huawei Health, Health Connect, full domain CRUD UI cutover, Sheets kill switch.

Exit

From a fresh clone, local Compose starts, migrates, seeds, passes auth/tenant/integration tests, survives restart and restores a backup without manual database steps. Only after this gate, a clean generic VPS is bootstrapped from the same repository artifacts; Git-SHA deploy/rollback and replacement-host restore pass inside RPO/RTO; Postgres is private, password/root SSH is disabled and logs contain no credentials.

B3 · Domain sync v1 (shopping core)
B3 — Products · Requests · Purchases on backend CORE

Перенос самого зрелого domain-контура (закупки) до Health Connect. Доменные инварианты текущей модели сохраняются, но порядок конфликтов больше не доверяет часам устройства: canonical revision назначает сервер.

# Work item Conflict / rule

3.2 Server entities + events: Request + lines Server version for request metadata; explicit field policy; lines unique by productId
3.3 Purchase responses multi-id merge Independent entities merged by responseId; unique idempotent operations
3.4 Client: write path through outbox for CRUD above Optimistic UI retained
3.5 Server version history for requests (optional local keep) Multi-device rollback foundation
3.6 Foreground pull + WorkManager sync; push notification may trigger pull One canonical pull path; no second WebSocket protocol in v1
3.7 Contract tests: merge fixtures from existing Node tests Reuse fixtures as transport-neutral golden cases; add concurrency/property tests
3.8 Notifications: new remote open request via backend push later; poll OK v1 Push carries no domain state; client always pulls canonical delta
3.9 Bootstrap snapshot + cursor, pagination, cursor expiry and RESET_REQUIRED Snapshot and cursor represent one consistent server revision
3.10 Tombstone retention + retired-device policy + schema negotiation GC exceeds supported offline window; incompatible clients receive upgrade-required
Exit

Randomized 3-device histories with offline edits, reorder, duplicate delivery, clock skew and delete/update races converge to one canonical state. Repeating every operation 10× creates one effect; multi-response purchases never collapse or double count; expired cursors recover through a verified bootstrap.

B5 · Ration v2 — facts, profile, adherence
B5 — Close the plan → shop → fact loop (no LLM) RATION

Самостоятельный продуктовый контур «план → покупка → факт». Он не зависит от AI; стабильные domain commands и read models сохраняют возможность добавить внешнего помощника после завершения этого плана.

# Work item UX / data
5.1 Ration sync on backend (days, meals, items, templates) Per-owner; conditional write by server meal version; timezone-aware day key
5.2 Meal log: eaten / partial / skipped / replaced One-tap on meal row; portionFactor
5.3 Ration profile: targets, exclusions, time budget, household size Profile or Ration settings
5.4 Adherence engine (deterministic) Versioned formula for 7d/30d; missing/partial/replaced semantics; kcal only when coverage is sufficient
5.5 Summary CTAs «N приёмов не отмечены», «Собрать список из рациона»
5.6 Request-from-ration remains first-class Must not regress package rounding
5.7 Partial UI updates for meal check (if not done earlier) Keep note-feel / no full re-render jank
5.8 Golden adherence dataset shared by client and server DST, timezone change, partial, skipped, replaced, missing nutrition and package units
5.9 Versioned read models and explicit commands for future external automation Read-only summaries + validated mutations; no agent runtime or AI-specific tables
Exit

User can plan a week, mark meals and see deterministic compliance across devices. Client and server produce identical 7d/30d results for the golden dataset, including DST and incomplete data. Zero LLM dependency and no AI UI/API.

B6 · Health Connect (optional first provider)
B6 — Versioned, normalized health daily summaries HEALTH CONNECT

Health Connect — единственная health-интеграция в текущем плане. Она опциональна для пользователя и не блокирует shopping/ration. Backend принимает provider-neutral summary DTO, но клиент реализует только источник health_connect.

# Work item Notes
6.1 Versioned health_summary schema + ingest API Upsert by user/source/localDay/type with sourceRevision and provenance; not immutable
6.2 Android Health Connect availability + permissions UX Steps, active calories, sleep, exercise; background/history are separate optional permissions
6.3 Aggregate reader + change-token sync Avoid double count; pagination, token expiry and bounded resync
6.4 Timezone, local-day and incomplete-day rules Store observed timezone, completeness and source data origins
6.5 Profile: connect / granted scopes / last sync / revoke / delete Health consent is independent from account and from any future AI scope
6.6 Retention enforcement + privacy copy + redacted telemetry No raw high-frequency series on backend; summaries deleted on revoke/account deletion per policy
6.7 Lifecycle tests Grant, partial grant, deny background/history, revoke, regrant, late correction, deletion, token expiry
6.8 Provider extension seam Document DTO and connector interface only; no Huawei dependency, flavor, scope or picker
Isolation

Отсутствие Health Connect, отказ в разрешениях или ошибка синхронизации никогда не блокируют вход, shopping, ration или backend sync.

Exit

User can opt in, see normalized yesterday summary and revoke access. Grant/revoke/regrant, provider corrections/deletions, change-token expiry and incomplete days produce correct state without double count. No AI consumer and no Huawei implementation exist.
