Итоговый вердикт

План хорош как стратегическая карта, но ещё не годится как исполнимый migration plan. Он правильно ставит backend и offline sync раньше AI/health, сохраняет текущие доменные инварианты и избегает big-bang UI rewrite. Однако B1 нельзя безопасно начинать, пока B0 не превратится из списка документов в набор принятых решений и исполняемых контрактных тестов.

Рекомендация: не менять направление, а добавить перед B1 короткий architecture spike и переписать exit criteria в измеримые release gates. B6–B8 оставить опциональными capability-треками, не включать их в обязательный cutover Sheets.

2 · Что в исходном плане сделано правильно
Architecture strengths
  • Backend source of truth вводится до agent harness и health.
  • Offline-first, outbox и clientOpId названы базовыми инвариантами.
  • Multi-response purchases не упрощаются до перезаписываемого receipt.
  • Meal log и deterministic adherence предшествуют AI-рекомендациям.
  • Agent apply отделён от preview и требует подтверждения пользователя.
  • Health provider abstraction позволяет не размножать backend-контракты.
Delivery strengths
  • Cutover вынесен в отдельный блок, а не смешан с CRUD.
  • Реальный household указан как exit B4 — это лучше лабораторной проверки.
  • AI и health не блокируют базовые shopping/ration flows.
  • Оставлены non-goals: scraping, medical coach, silent overwrite.
  • Наличие ADR/OpenAPI/fixtures в B0 — правильная форма артефактов.
  • Huawei approval lead time замечен заранее.

Исправить противоречие исходного summary

В метрике исходного отчёта critical path обозначен как B0→B4→B5, хотя фактическая диаграмма требует B0→B1→B2→B3→B4→B5. Краткая запись скрывает самые рискованные работы — storage и sync — и должна быть заменена полным путём.

7 · Минимальный sync-контракт, которого не хватает
Operation envelope
  • schemaVersion, householdId, deviceId, clientOpId.
  • entityType, entityId, operation, payload и baseVersion.
  • Server назначает serverRev; client timestamp остаётся метаданными, а не арбитром порядка.
  • Unique constraint (household_id, client_op_id) делает retry идемпотентным.
  • Batch ack возвращает applied/rejected/conflict и canonical entity/version.
Cursor lifecycle
  • Первичная загрузка: consistent snapshot + cursor одной транзакции.
  • Pull: opaque cursor, stable ordering, pagination и repeat-safe delivery.
  • Compaction: cursor expiry возвращает явный RESET_REQUIRED.
  • Tombstones хранятся дольше max offline window; retired devices не удерживают GC бесконечно.
  • Schema incompatibility не маскируется retry — приложение получает upgrade-required.
Критическая правка conflict policy

Нельзя переносить текущий LWW by updatedAt на backend буквально: часы устройств не являются доверенным глобальным порядком. Для request metadata и ration meal следует использовать server version / conditional write; независимые response entity продолжают merge по responseId. Для полей, где одновременные правки допустимы, policy должна быть записана по полям, а не только по entity.

8 · Agent и health: реализуемость по платформам
B6 · Agentfeasible

grok-4.5 в актуальной документации поддерживает function calling и structured outputs, поэтому выбранный harness технически реалистичен. Но модель надо считать сменным провайдером: pin конкретной версии, capability check, quotas, cost telemetry и provider-neutral tool schemas.

Транспорт: выбрать async job + resumable SSE для foreground UX; состояние job хранить на сервере. WebSocket не нужен как обязательный второй путь. Apply — отдельная транзакция с idempotency key и optimistic precondition на ration revision.

B7 · Health Connectfeasible with constraints

Health Connect поддерживает фоновые чтения только с отдельным разрешением и feature availability check; aggregates рекомендованы для steps, чтобы избегать double count. История старше стандартного окна также требует отдельного разрешения.

Следствие: sync должен работать частично при отказе в background/history, хранить provenance и обрабатывать changes-token expiry. «Immutable by source+day+type» заменить на versioned upsert: health providers корректируют и удаляют прошлые записи.

B8 · Huawei Healthearly spike required

Официальная документация описывает device-side чтение из Huawei Health с consent, установленным Huawei Health и ограниченной матрицей устройств/OS/регионов. На странице совместимости, актуальной в мае 2026, для phone указан Android 6–13, тогда как Cookish targetSdk — 36. Это не доказывает несовместимость на новых устройствах, но делает B8 отдельным feasibility risk.

Корректировка: начать не только paperwork, а минимальный signed APK spike в B0/B1; проверить реальное Huawei-устройство, Android/EMUI/HMS версии, регион аккаунта, доступные scopes и публикационную модель. При неуспехе B8 не должен задерживать Architecture v2.
